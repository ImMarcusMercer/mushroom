# MushroomFarm ESP32 Sensor Network

This project is a refactored Arduino-code version of the previous engineers' MushroomFarm monitoring system. The current goal is to validate that a **ZY-ESP32 main controller** can receive and display multiple physical sensor readings from an **ESP32-C3 SuperMini node** over Wi-Fi/HTTP without changing the overall legacy architecture.

## Current test target

The immediate bench test is **Node 1 -> Main**.

- **Main:** ZY-ESP32 / classic ESP32
- **Node 1:** ESP32-C3 SuperMini, ID `sensor1`
- **Node 2:** ESP32-C3 SuperMini, ID `sensor2`
- **Node 3:** ESP32-C3 SuperMini, ID `sensor3`
- **Current active sensors per node:**
  - 3 x VEML7700 light/lux sensors
  - 1 x DHT11 temperature/humidity sensor
- **Moisture sensing:** code retained but disabled for now
- **Future target per node:**
  - 9 x VEML7700
  - 3 x moisture sensors

The Main remains the Wi-Fi access point and HTTP server. Nodes connect directly to the Main and POST JSON to:

```text
http://192.168.4.1/data
```

## Architecture

```text
                    Wi-Fi AP: MushrooMan
                    Main IP: 192.168.4.1

 ESP32-C3 Node 1  ───────┐
 ESP32-C3 Node 2  ───────┼──── HTTP POST /data ────> ZY-ESP32 MAIN
 ESP32-C3 Node 3  ───────┘                               │
                                                         ├── TFT display
                                                         ├── SD card
                                                         ├── DS3231 RTC
                                                         ├── MCP23017
                                                         ├── relay outputs
                                                         ├── local web UI
                                                         └── CSV logging
```

There is no direct UART/SPI/I2C cable between Main and Nodes. Node-to-Main data transport is Wi-Fi.

## Legacy Main flow preserved

`main/main.ino` preserves the previous codebase's main operating flow:

1. Main boots and initializes TFT, SD, RTC, MCP23017, relay outputs, and display button.
2. Main creates Wi-Fi AP `MushrooMan`.
3. Main starts its HTTP server.
4. Nodes join that AP.
5. Nodes POST JSON to `/data`.
6. Main stores the latest readings in RAM.
7. Main updates the TFT and local web interface.
8. DHT temperature/humidity can continue through the existing temp/humidity path.
9. Lux data uses the added multi-sensor array path.
10. Historical data is grouped and later written to SD.
11. Relay automation, stale-node handling, C3 power cycling, RTC scheduling, and manual override behavior remain present.

## Current Node packet

The current Node sketches send a packet approximately like this every 5 seconds:

```json
{
  "id": "sensor1",
  "seq": 42,
  "uptime_ms": 210345,
  "temp": 27.0,
  "hum": 78.0,
  "lux": [123.45, 118.90, 131.22],
  "moisture_raw": []
}
```

Important points:

- `temp` and `hum` come from the physical DHT11.
- `lux[]` comes from the physical VEML7700 sensors.
- `moisture_raw` is deliberately an empty array because moisture sensing is disabled.
- If DHT11 or a VEML7700 read fails, that value is sent as JSON `null` instead of inventing a reading.
- No random or simulated readings are generated by normal node operation.

## Why moisture is still present in the protocol

Moisture support is not deleted. The following remain in the Node/Main code:

- future moisture GPIO assignments
- raw ADC read function
- Main moisture array parsing
- Main moisture storage structures
- future CSV fields

On the Nodes, this switch controls whether moisture is active:

```cpp
const bool ENABLE_MOISTURE = false;
```

For the current test, leave it `false`.

## Main TFT pages

The Main currently cycles through three pages using the existing button:

```text
Page 1 -> Temperature / Humidity
Page 2 -> Legacy Spectrometer / Treatment display
Page 3 -> DHT11 + 3-Lux Node test
```

Page 3 is the easiest screen for validating the current multi-sensor test because it shows:

- Node ID
- DHT11 temperature
- DHT11 humidity
- Lux 1
- Lux 2
- Lux 3
- packet sequence number
- age of the latest packet

The browser interface at `http://192.168.4.1` also shows the current Node DHT11/lux data.

## TFT_eSPI requirement

The legacy Main wiring specifies:

```text
MOSI 23
MISO 19
SCK  18
CS   5
```

The previous document does not identify the TFT controller, DC pin, or reset pin. Those values are usually configured in `TFT_eSPI`'s `User_Setup` file.

Use the same TFT_eSPI driver/DC/RST configuration already known to work with the existing ZY-ESP32 hardware. Do not guess those values if the previous Main already has a known working display configuration.

## Node 1 -> Main test procedure

### 1. Upload Main

Upload:

```text
main/main.ino
```

Open Serial Monitor at:

```text
115200 baud
```

Main should create:

```text
SSID: MushrooMan
Password: RABE2026qt
IP: 192.168.4.1
```

For the current test, Main only requires `sensor1` to remain online. `sensor2` and `sensor3` code are included but are not required during the first test.

### 2. Wire Node 1

Connect:

```text
ESP32-C3 GPIO4 -> TCA9548A SDA
ESP32-C3 GPIO5 -> TCA9548A SCL
ESP32-C3 GPIO6 -> DHT11 DATA

TCA CH0 -> VEML7700 #1
TCA CH1 -> VEML7700 #2
TCA CH2 -> VEML7700 #3
```

Use 3.3 V logic on the ESP32-C3 side. See `SCHEMATICS.md` for detailed wiring.

### 3. Upload Node 1

Upload:

```text
node1/node1.ino
```

Open its Serial Monitor at 115200 baud.

A successful startup should show approximately:

```text
Node ID: sensor1
Test sensors: 3x VEML7700 + 1x DHT11
Moisture: DISABLED (code retained)
Lux 1: OK
Lux 2: OK
Lux 3: OK
Connected. Node IP: ...
```

Every ~5 seconds it should print a real JSON packet and then:

```text
Main response: HTTP 200 - OK
```

### 4. Verify Main receives the Node

Main Serial Monitor should show values similar to:

```text
Data received from sensor1
  Temp: 27.00 C
  Hum: 78.00 %
  Lux: 123.45, 118.90, 131.22
  Seq: 42
```

### 5. Verify display and browser UI

On the Main TFT, cycle to the Node page using the GPIO33 button.

The Node page should show the DHT11 and three lux values.

You can also connect a phone/laptop to `MushrooMan` and open:

```text
http://192.168.4.1
```

The Live Node Data table should show the same measurements.

## Testing Node 2 and Node 3 later

The three node sketches differ only by identity:

```text
node1 -> sensor1
node2 -> sensor2
node3 -> sensor3
```

After Node 1 is confirmed, wire Node 2 and Node 3 the same way and upload their respective sketches.

Then change in `main/main.ino`:

```cpp
const int EXPECTED_C3_COUNT = 1;
```

to:

```cpp
const int EXPECTED_C3_COUNT = 3;
```

This enables stale-node/power-cycle monitoring for all three Nodes.

## Future expansion to 9 lux + 3 moisture sensors

The current structures are already sized for:

```text
Lux1 ... Lux9
Moisture1 ... Moisture3
```

The intended lux topology is:

```text
TCA9548A #1 address 0x70
  CH0 -> Lux1
  CH1 -> Lux2
  CH2 -> Lux3
  CH3 -> Lux4
  CH4 -> Lux5
  CH5 -> Lux6
  CH6 -> Lux7
  CH7 -> Lux8

TCA9548A #2 address 0x71
  CH0 -> Lux9
```

Future moisture pins reserved in the node code are:

```text
GPIO0
GPIO1
GPIO3
```

Do not enable them until the exact moisture hardware and calibration method are confirmed.

## Current test success criteria

The current architecture passes the first test when all of these are true:

- Node 1 joins the Main AP.
- Main returns HTTP 200 to Node 1.
- Main receives one DHT11 temperature value.
- Main receives one DHT11 humidity value.
- Main receives three independent VEML7700 values.
- Main TFT displays the readings.
- Browser UI displays the readings.
- Sequence numbers continue increasing without unexplained resets.
- Main does not falsely report Node 1 stale while packets continue arriving.

Once these pass, the same transport/data design can be tested with Nodes 2-3 and then scaled toward the planned sensor count.


## Main ESP32 RAM note

The ZY-ESP32/classic ESP32 main uses internal DRAM for global/static buffers. The original reconstructed values (`MAX_HISTORY_ENTRIES = 800` and `MAX_NODE_HISTORY_ENTRIES = 240`) can overflow the linker DRAM region when combined with Wi-Fi, WebServer, TFT_eSPI, ArduinoJson, SD, RTClib, and MCP23X17.

For the current bench build the buffers are intentionally set to:

- `MAX_HISTORY_ENTRIES = 300`
- `MAX_NODE_HISTORY_ENTRIES = 72`

This preserves the hourly logging flow while leaving substantially more internal RAM headroom. For a future production refactor, prefer streaming CSV rows to SD (or using PSRAM only on a board that actually has PSRAM) instead of increasing large static arrays.
